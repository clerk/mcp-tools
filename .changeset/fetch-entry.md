'@clerk/mcp-tools': minor

Add `@clerk/mcp-tools/fetch`, an entry for plain `fetch` Workers such as Cloudflare Workers. It has the same `clerkInstrumentHandler` and `clerkInstrumentServer` as the other adapters. Its `clerkInstrumentHandler(handler, options)` adds Clerk auth to an MCP handler and returns a `(request, env, ctx)` function. The handler can be the one `createMcpHandler` from `@modelcontextprotocol/server` returns, or any `fetch`-style MCP handler. A function handler is called with `{ authInfo, env, ctx }`. A request without a valid token gets the `401` challenge. Tokens are verified with the resource URL as their audience. The protected resource metadata the challenge points to is served at the RFC 9728 metadata URL of each listed resource URL, path and query included. Every other path or query, such as the bare well-known root, goes to the handler. A method other than `GET` or `HEAD` on the metadata URL gets an uncached `405`. It takes the options of the Next.js `clerkInstrumentHandler`, including `onAuthFailure` and `reporting`. With `reporting`, it reports MCP activity and auth failures as the other adapters do. The reports are sent with `ctx.waitUntil` once the response is over. On Cloudflare they include the client's `cf-connecting-ip`. Clerk keys, for verifying tokens and for reporting, come from the options or the Worker `env` passed to `fetch`. The entry never reads `process.env`. It caches the Clerk client per set of keys. It imports no MCP SDK. The Hono adapter's `clerkInstrumentHandler` now reads its Clerk keys and caches its Clerk clients through the same shared core as this entry. Its behaviour is unchanged: it still reads its keys from `env(c)`, keeps one client per set of keys, and throws the same errors.
