'@clerk/mcp-tools': minor

Add `@clerk/mcp-tools/fetch`, an entry for plain `fetch` Workers such as Cloudflare Workers, with the same `clerkInstrumentHandler` and `clerkInstrumentServer` as the other adapters. Its `clerkInstrumentHandler(handler, options)` serves the handler `createMcpHandler` from `@modelcontextprotocol/server` returns, or any `fetch`-style MCP handler, with Clerk auth, and returns a `(request, env, ctx)` function: it answers requests without a valid token with the `401` challenge, serves the protected resource metadata the challenge points to at the RFC 9728 metadata URL, path and query, of each listed resource URL (passing every other path or query, such as the bare well-known root, to the handler, and answering another method than `GET` or `HEAD` with an uncached `405`), verifies tokens with the resource URL as their audience, and calls a function handler with `{ authInfo, env, ctx }`. It takes the options of the Next.js `clerkInstrumentHandler`, `onAuthFailure` and `reporting` included: with `reporting`, it reports MCP activity and auth failures as the other adapters do, sent with `ctx.waitUntil` once the response is over, with the client's `cf-connecting-ip` on Cloudflare. Clerk keys, for verifying tokens and for reporting, are read from the options or the Worker `env` passed to `fetch`, never `process.env`, and the Clerk client is cached per set of keys. It imports no MCP SDK. The Hono adapter's `clerkInstrumentHandler` now reads its Clerk keys and caches its Clerk clients through the same shared core as this entry, with no change in behaviour: it still reads its keys from `env(c)`, keeps one client per set of keys, and throws the same errors.
