'@clerk/mcp-tools': minor
---

**Breaking:** every entry point has a new, consistent API, following `@clerk/express`, `@clerk/hono`, `@clerk/nextjs`, and `@clerk/backend`. Functions are named for what they do, without a `Clerk` suffix: Clerk is the default, and another authorization server is an option. Configuration types end in `Options`. The old names are removed with no deprecated aliases. Each adapter (`./express`, `./hono`, `./next`) also re-exports everything from `./server`, so a server imports from its adapter alone.

`mcpAuth` (and `withMcpAuth` in Next.js) takes one `McpAuthOptions` object. Without `verifyToken`, Clerk verifies the token and `resourceUrl` is required. `clerkClient` is optional in every adapter, and takes a Clerk client or a function that returns one (or a promise of one), called once for each request. A value without `authenticateRequest` throws a `Clerk error:` when `mcpAuth` or `withMcpAuth` is called. It defaults to `clerkClient` from `@clerk/express` in Express, a client built from `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` in Hono, and `clerkClient` from `@clerk/nextjs/server`, loaded on the first request, in Next.js. With `verifyToken(token, req)`, your function returns the MCP SDK's `AuthInfo`, or `undefined` to reject the token, and `resourceUrl` is optional. Pass the same options object to `protectedResourceMetadataHandler`, which ignores the verification options. In Express, `streamableHttpHandler` takes `StreamableHTTPServerTransport` from `@modelcontextprotocol/sdk/server/streamableHttp.js`. In Hono, it takes `WebStandardStreamableHTTPServerTransport`, from `@modelcontextprotocol/sdk/server/webStandardStreamableHttp.js` on SDK 1.x or from `@modelcontextprotocol/server` on SDK 2.x, where `scopeChallenge` step-up works through it.

### Behavior changes

- **Audience check.** When Clerk verifies the token, `mcpAuth` and `withMcpAuth` now check that the token's audience is `resourceUrl`. A token issued for another resource no longer passes. Set `resourceUrl` to the exact URL clients use for the endpoint. Your Clerk instance must issue the `aud` claim; the Clerk Dashboard turns it on when you add the instance's first MCP server. A token without `aud`, or with one that doesn't name this server, gets a `401` `invalid_token` challenge, and a client that keeps getting the same token loops on that `401`. That affects servers set up from the older guide without an MCP server in the Dashboard, refresh grants issued before `aud` was turned on, and clients that never send the `resource` parameter (RFC 8707 section 2). Because of this check, the peer dependencies now start at `@clerk/express` 2.1.70, `@clerk/nextjs` 7.9.5, and the optional `@clerk/backend` 3.19.0.
- **Next.js metadata `resource`.** `protectedResourceMetadataHandler` sets `resource` from the route path, so `/.well-known/oauth-protected-resource/mcp` describes `<origin>/mcp` instead of the bare origin. New tokens carry `<origin>/mcp` in `aud`. Tokens issued before the upgrade carry the origin, so `withMcpAuth` answers them with a `401` `invalid_token` challenge and the client authorizes again. To keep the origin as the resource instead, pass `resourceUrl: origin` to both `withMcpAuth` and `protectedResourceMetadataHandler`, and serve the metadata at the root `app/.well-known/oauth-protected-resource/route.ts`, where `withMcpAuth`'s challenge then points.
- **Protected resource metadata fields.** Metadata now holds only `resource`, `authorization_servers`, `bearer_methods_supported`, and any `properties`, as RFC 9728 section 2 defines them. `jwks_uri`, `token_types_supported`, the `token_introspection_*` fields, `authorization_data_*`, and `key_challenges_supported` are removed. `service_documentation` (`https://clerk.com/docs`) is removed; pass `resource_documentation` in `properties` for a page about your server. `properties` can no longer set `resource`: in 0.9.0, `properties.resource` replaced `resourceUrl`, so the metadata could name a resource other than the one the server protects, and a client discards metadata whose `resource` is not the URL it derived the metadata URL from (RFC 9728 section 3.3). `generateProtectedResourceMetadata` throws a `Clerk error:` when `properties` has its own `resource` key, even one set to `undefined`, and `protectedResourceMetadataHandler` throws it when the handler is created. Remove `resource` from `properties` and pass that URL as `resourceUrl`. `scopes_supported` defaults to `requiredScopes` plus `challengeScopes`. A `scopes_supported` you pass must include all of them.
- **Errors.** When a verifier throws anything other than `McpTokenVerificationError`, the error is wrapped in an `McpAuthError` with `reason: 'verification_failed'`, and the original error is its `cause`. The `McpAuthError`'s `status` is the cause's `status` only when it is the integer `429` or an integer from `500` to `599`. Every adapter answers it with a JSON `{"error":"server_error"}` and that status, or `500` when it has none, instead of a framework error page (Express's default one is HTML with the stack trace outside production), and logs the `McpAuthError` with `console.error`. Express answers it in `mcpAuth` and doesn't pass it to error middleware, whose default handler would reset a connection that is still uploading its body. Hono throws it to `app.onError`, and its default handler answers and logs it; a custom `onError` replaces both, so answer the same way there. Next.js `withMcpAuth` answers it itself, so `onRequestError` doesn't see it. When Clerk cannot verify an opaque token at all, for example during an outage, when it rate-limits the server, or with an invalid secret key, the result is that server error instead of `invalid_token`, so clients keep a valid token. A JWT access token gets it when Clerk's signing keys can't be loaded. With current `@clerk/backend` releases that is only when the request for the signing keys is answered with an error status and a JSON body: they report every other failure to load them, such as an invalid secret key, a network error, or an error page that is not JSON, as they report an invalid signature, so those still get `invalid_token`. Once clerk/javascript#10826 ships, `@clerk/backend` reports those failures with the reason `jwk-remote-failed-to-load`, and each of them gets the server error. The `McpAuthError`'s message is `MCP access token verification failed`, without a `Clerk error:` prefix, because the verifier can be your own `verifyToken`. Clerk verification puts the Backend API's status on `McpTokenVerificationError.status`, so a `503` or `429` from Clerk is forwarded, and a Backend API `4xx` other than `401` and `429` is treated as a rejected token (`401 invalid_token`).
- **Authorization server metadata errors.** `fetchAuthorizationServerMetadata`, and so `authorizationServerMetadataHandler`, now throws a `Clerk error:` when the Frontend API answers with a non-2xx status, instead of serving its error body as the metadata.
- **Metadata headers in Express and Hono.** `protectedResourceMetadataHandler` and `authorizationServerMetadataHandler` in `./express` and `./hono` now send the headers the `./next` handlers send: `Cache-Control: max-age=3600` and the `metadataCorsHeaders` CORS headers, which allow any origin, on the metadata, and the CORS headers alone, with no caching, on an error such as the `421` or `502`. Mounted for `OPTIONS` as well as `GET`, with `app.all` (or `app.use` in Express), they answer the CORS preflight with a `200` and the CORS headers. A browser-based MCP client fetches the metadata cross-origin, so it can now read it from any adapter. In Express they replace the CORS headers that a middleware mounted before them set on those routes. In Hono it is the other way round: on the `GET`, the headers a `cors()` middleware in front of them sets, such as its `Access-Control-Allow-Origin`, are kept in place of the handlers' own, and `cors()` answers the preflight itself.
- **Stateless `streamableHttpHandler`.** `streamableHttpHandler` in `./express` and `./hono` now answers any request that isn't a `POST` with a `405`, `Allow: POST`, and the JSON-RPC `Method not allowed.` error, the answer MCP SDK 2's stateless serving gives. It serves each request on a new stateless transport, so a `GET` has no session to stream on, and in 0.9.0 the SDK 1 transport opened a stream that nothing wrote to. The examples now mount the endpoint with `app.all('/mcp', ...)`, so a `GET` without a token reaches `mcpAuth` and gets the `401`, or the `405` when `publicAccess` opens the handshake, rather than the framework's `404`.
- **Expired tokens.** A token whose `expiresAt` has passed now gets an `invalid_token` challenge, even when `verifyToken` returned its auth info.
- **Express `clerkMiddleware()`.** The Express `mcpAuth` no longer reads the auth that `clerkMiddleware()` set through `getAuth()`. Without `clerkClient`, it verifies each token itself with `clerkClient` from `@clerk/express`, which reads `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` from the environment. If you configured `clerkMiddleware()` with explicit keys or a client instead, pass a client to `mcpAuth` too, as `mcpAuth({ resourceUrl, clerkClient: createClerkClient({ secretKey, publishableKey }) })` with `createClerkClient` from `@clerk/express`. `clerkMiddleware()` is no longer needed on the MCP route, and left there it verifies each token a second time. `@clerk/express` is now loaded on the first request, and only when `mcpAuth` uses that default client, so an app that passes `verifyToken` or `clerkClient` no longer needs it installed. A missing `CLERK_SECRET_KEY` or `CLERK_PUBLISHABLE_KEY` now throws a `Clerk error:` setup error on every request, as in Hono, instead of a `500` once a token arrives. In Next.js, without a `clerkClient` option, a missing `CLERK_SECRET_KEY` or `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` does the same.
- **Duplicate `Authorization` headers.** A request with more than one `Authorization` header gets the `401` challenge in every adapter. The Express `mcpAuth` used to verify the first one.
- **`toClerkAuthInfo` logging.** `toClerkAuthInfo`, which replaces `verifyClerkToken`, no longer logs `Invalid OAuth access token` with `console.error` for an unauthenticated auth object; it returns `undefined` silently.
- **`@clerk/hono`.** The Hono adapter no longer uses `@clerk/hono`, and it is no longer a peer dependency. Without `clerkClient`, `mcpAuth` builds its own client and ignores one that `clerkMiddleware()` set.
- **Hono `mcpAuth` variable.** `c.get('mcpAuth')` is now typed `AuthInfo | undefined`, because a request that `publicAccess` lets through has no auth info.
- **Next.js Pages Router.** The Next.js handlers are App Router route handlers. The README no longer suggests they work from Pages Router API routes, which they never did.
- **MCP SDK.** `@modelcontextprotocol/sdk` is now an optional peer dependency. The server entry points never import it. `./client` and `./next/client` require it at 1.29 or later in your own dependencies. Express and Hono apps that import it, for example `McpServer` for `streamableHttpHandler`, must list it in their own dependencies too, or `@modelcontextprotocol/server` for a Hono app on SDK 2: 0.9.0 depended on it, so a package manager that hoists dependencies, such as npm, may have installed it for an app that never listed it, and after the upgrade the import fails with `Cannot find module`.

### Removed

- `protectedResourceHandler`, the metadata handler for an authorization server other than Clerk. For another server, serve `generateProtectedResourceMetadata({ resourceUrl, authServerUrl })` from your own route.
- The tool schemas and helpers `SUBMIT_FEEDBACK_DESCRIPTION`, `submitFeedbackInputSchema`, `FEEDBACK_KINDS`, `FEEDBACK_IMPACTS`, `FeedbackToolExtra`, `browserSessionInputSchema`, `browserSessionToolText`, `browserSessionErrorMessage`, and `validateBrowserSessionOptions`. Register a tool with `server.registerTool(...submitFeedbackTool({ secretKey }))`, and customise it by overriding the config it returns and wrapping its callback. Use the `FeedbackKind` and `FeedbackImpact` types in place of `FEEDBACK_KINDS` and `FEEDBACK_IMPACTS`. `SUBMIT_FEEDBACK_TOOL_NAME` and `CREATE_BROWSER_SESSION_TOOL_NAME` are still exported.
- The `main` field of `package.json`. Import a subpath.

### New

- `requiredScopes` are the scopes every request needs, and `challengeScopes` adds scopes, such as the ones individual tools step up to, to the `401` challenge without requiring them. The `401` challenge's `scope` lists `requiredScopes` then `challengeScopes`, each once. A token missing a `requiredScopes` entry gets a `403` `insufficient_scope` challenge whose `scope` lists the token's granted scopes followed by every missing `requiredScopes` and `challengeScopes` entry, each once, so the new grant keeps the old access. List each tool's `requireAdditionalScopes` scopes in `challengeScopes` to have the client reauthorize once for the `403` and the tool, as MCP 2026-07-28 asks of scope challenges. Only a missing `requiredScopes` entry gets the `403`: a token that lacks only `challengeScopes` entries is let through.
- `publicAccess` on `mcpAuth` and `withMcpAuth` names what a request without a token may do: `methods` (`true`, or a list of protocol and list methods), `tools` (tool names), and `resources` and `prompts` (`true`, or a list of resource URIs or prompt names). A client can then connect and call the tools you list without signing in, and gets the `401` challenge when it reaches anything else. Nothing is open without it. With the handshake open, a `GET` without a token gets a `405` instead of the challenge, so a client does not start authorization by opening its stream: with `initialize` or `server/discover` open, a tokenless `GET` gets a `405` with `Allow: POST` and the JSON-RPC body `streamableHttpHandler` sends, so a `GET` gets one answer whether or not it carries a token, and a tokenless `subscriptions/listen` (2026-07-28) passes when every resource it subscribes to is open. In Express, mount `express.json()` before `mcpAuth` to use it. The new `PublicAccess` and `McpPublicMethod` types are exported from `./server` and every adapter.
- `resourceUrl` can be a list of URLs, one for each origin. A request to an origin that is not listed gets a `421`. `matchResourceUrl` applies the same rule in a route of your own.
- Auth failures are reported for logging: in `res.locals.mcpAuthFailure` in Express, in `c.get('mcpAuthFailure')` in Hono, and through `onAuthFailure(failure, req)` in Next.js. `onAuthFailure` is a synchronous notification whose return value is ignored; schedule asynchronous logging with Next.js `after()` to keep it alive after the response without delaying the challenge.
- In Hono, `mcpAuth({ resourceUrl })` works without `clerkMiddleware()`. It builds a client from `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` through `env(c)`, which requires `@clerk/backend`.
- The auth info now carries `resourceMetadataUrl`, which MCP SDK 2 step-up challenges need.
- Auth info from `toClerkAuthInfo`, and so from Clerk verification in `mcpAuth` and `withMcpAuth`, keeps Clerk's own auth object for the token on `extra.auth`, with fields such as `id`, `subject`, and `getToken()`. After `isClerkAuthInfo(authInfo)`, it is typed as the new `ClerkOAuthAuth`. `toClerkAuthInfo` returns `undefined` for an auth object without `id`, `subject`, or `getToken`, which Clerk always sets. `ClerkAuthInfo.extra.auth` is optional, so `AuthInfo` built by hand without it still type-checks.
- New exports: `McpAuthError`, `McpTokenVerificationError`, and the `McpAuthOptions`, `ProtectedResourceMetadataOptions`, `McpResourceUrl`, `McpAuthFailure`, and `ClerkOAuthClient` types. `@clerk/mcp-tools/package.json` is importable.
- `createBrowserSessionTool` takes `organizationId`, an ID or a function, synchronous or `async`, that returns one for each call from the verified auth info, run after the auth, scope, and path checks. When the function throws or returns anything but a non-empty string or `undefined`, the tool refuses with the new `organization_lookup_failed` code; a thrown `BrowserSessionError` keeps its own code. Its options type is the new `CreateBrowserSessionToolOptions`.
- Every error result of `create_browser_session` and `submit_feedback` carries a code in `_meta[ERROR_CODE_META_KEY]` (`'clerk.com/error_code'`, exported from `./tools`), so a wrapper can tell failures apart without reading the text: the `BrowserSessionErrorCode` or `unexpected_error` for `create_browser_session`, and `rate_limited`, `rejected`, or `unconfirmed` for `submit_feedback`.
- New `./tools` types: `FeedbackKind`, `FeedbackImpact`, and `CreateBrowserSessionToolOptions`. `FeedbackReport.kind` and `impact` are typed with them, and still accept other slugs.
