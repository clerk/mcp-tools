---
'@clerk/mcp-tools': minor
---

**Breaking:** in `@clerk/mcp-tools/express` and `@clerk/mcp-tools/hono`, `mcpAuthClerk` is now a factory that takes `{ resourceUrl, requiredScopes }`. It verifies OAuth access tokens with Clerk and checks that their audience is `resourceUrl`. The old middleware did not check the audience, so a token issued for another resource passed. Replace `app.post('/mcp', mcpAuthClerk, handler)` with `app.post('/mcp', mcpAuthClerk({ resourceUrl: 'https://mcp.example.com/mcp' }), handler)`, using the exact URL clients use for the endpoint. The peer dependency ranges now start at `@clerk/express` 2.1.70 and `@clerk/hono` 0.1.80, because on earlier versions a JWT access token without an `aud` claim and an opaque OAuth access token both pass the audience check.

In both adapters, `mcpAuthClerk` takes an optional `clerkClient`, created with both `secretKey` and `publishableKey`. The Express `mcpAuthClerk` defaults to `clerkClient` from `@clerk/express`; pass the client you gave `clerkMiddleware()` when the secret key does not come from `CLERK_SECRET_KEY`. The Hono `mcpAuthClerk` defaults to the client `clerkMiddleware()` sets; pass a client to keep `clerkMiddleware()` off the MCP route, which otherwise verifies each token twice. In both adapters, when Clerk cannot verify an opaque access token at all, for example during an outage or with an invalid secret key, `mcpAuthClerk` throws to the framework's error handler for a `500` instead of answering `invalid_token`, which would make clients discard a valid token and restart authorization. Clerk reports a JWKS failure on a JWT access token the same way as an invalid signature, so that case still answers `invalid_token`.

`mcpAuth` in both adapters takes new optional `resourceUrl` and `requiredScopes` options. A token without `requiredScopes` gets a `403` with an `insufficient_scope` challenge, and `resourceUrl` sets the challenge's `resource_metadata` instead of deriving it from the request. The auth info both adapters pass on now carries `resourceMetadataUrl`, which MCP SDK 2 needs for the challenges its `scopeChallenge` tools send.

In every adapter, the `401` challenge from `mcpAuth` and `mcpAuthClerk` (`withMcpAuth` in Next.js) now lists `requiredScopes` in its `scope`, and the new `challengeScopes` option adds more, such as the scopes tools step up to, without requiring them of a token. MCP clients request those scopes when they first authorize. A request the middleware answers itself, with a `401` or `403` challenge or a `421`, records why in `res.locals.mcpAuthFailure` in Express and `c.get('mcpAuthFailure')` in Hono, and is passed to the new `onAuthFailure(failure, req)` option in Next.js, whose errors and rejections are ignored so that the answer still goes out, with a `reason` of `missing_token`, `malformed_token`, `invalid_token`, `insufficient_scope`, or `misdirected_request`, for logging. Every adapter also exports `McpTokenVerificationError`, which holds what a verifier reported for a token it did not accept. Under `mcpAuthClerk`, its `code` is the reason Clerk gave, such as `token-verification-failed`, and its `message` is Clerk's message. It is the `cause` of an `invalid_token` failure for a token Clerk rejected, and the `cause` of the `McpAuthError` thrown when Clerk answers but cannot verify a token. A `verifyToken` passed to `mcpAuth` can throw one to reject a token with a code of its own. It is never sent to the client.

In every adapter, `resourceUrl` for `mcpAuth` and `mcpAuthClerk` (`withMcpAuth` in Next.js) can also be a list of URLs, one for each origin, for a server that answers on several hostnames. A request uses the listed URL with its origin for the challenge's `resource_metadata` and, in `mcpAuthClerk`, as the only audience, so a token issued for one listed URL does not pass on another. A request to any other origin gets a `421 Misdirected Request` before its token is read. `matchResourceUrl` from `@clerk/mcp-tools/server` applies the same rule, so a protected resource metadata route can set `resource` to the URL the middleware checks.

**Breaking:** in the Express and Hono adapters, when the verifier throws anything other than an `McpTokenVerificationError`, `mcpAuth` and `mcpAuthClerk` now throw an `McpAuthError`, exported from each adapter, with `reason: 'verification_failed'` and the thrown error as its `cause`, instead of the thrown error itself. The new Next.js wrappers do the same. An error handler that checks `err instanceof MyError` or reads the error's fields, including Hono's `HTTPException` handling, must read `err.cause` instead. The wrapper copies a `5xx` `status` from the thrown error, so Express's default error handler answers with it as before. Any other status is dropped and the answer is a `500`: before, a thrown error with `status: 401` reached the client as a `401` without a challenge.

`resourceUrl` can no longer have a fragment, and a query in it is now kept in the challenge's `resource_metadata`. `mcpAuthClerk` also accepts a token whose audience is the normalized form of `resourceUrl`, such as `https://mcp.example.com/` for `https://mcp.example.com`, since clients can send either, and for a root `resourceUrl` written with a trailing slash it also accepts the bare origin, which the root protected resource metadata route describes. In the Express adapter, a request without a `Host` header, or with one that does not parse, gets a `400` instead of an unhandled error or a challenge for `http://undefined`, and the request's origin comes from `req.host`, so under `trust proxy` it is read from `X-Forwarded-Host`. Each adapter now exports the `McpAuthOptions`, `McpAuthClerkOptions`, `McpResourceUrl`, `McpAuthFailure`, and `ClerkOAuthClient` types, and `@clerk/mcp-tools/next` exports `McpRouteHandler`, the type of the route handler its wrappers take, and `WithMcpAuthOptions`.

`@clerk/backend` 3.19.0 or later is a new optional peer dependency, for the version of a client you pass as `clerkClient`: a client from an earlier version does not reliably check the audience. This package's types do not reference it, so an app that has only `@clerk/express`, `@clerk/hono`, or `@clerk/nextjs` type-checks without it. The `clerkClient` option takes the new `ClerkOAuthClient` type, the part of a Clerk client that verifies tokens, and `verifyClerkToken` in `@clerk/mcp-tools/server` and `@clerk/mcp-tools/next` takes the new `ClerkOAuthAuthObject` from `@clerk/mcp-tools/server` in place of `MachineAuthObject<'oauth_token'>`, which still fits it.

The `WWW-Authenticate` challenge from both adapters now quotes `resource_metadata`, which was invalid unquoted, and a rejected token now gets the challenge with `error="invalid_token"` instead of no header.

In the Express adapter, `mcpAuth` is now synchronous, so it works with or without `await`. A malformed `Authorization` header now gets a `401` challenge: before, a bare `Bearer` header returned a `500`, or hung the request with an unhandled rejection under `mcpAuthClerk`, and any other scheme was treated as a bearer token. `resource_metadata` no longer includes the request's query string.

**Breaking:** in `@clerk/mcp-tools/next`, `protectedResourceHandler` now sets `resource` from the route path and query, so `/.well-known/oauth-protected-resource/mcp` describes `<origin>/mcp` instead of the bare origin, and `/.well-known/oauth-protected-resource/mcp/` describes `<origin>/mcp/`. MCP clients send that value as the `resource` of their token request, so new tokens carry `<origin>/mcp` in their `aud` claim, and a route that checks `audience: origin` rejects them. Check the audience against the full `<origin>/mcp` URL. Tokens issued before the upgrade still carry the origin, so accept both with ``audience: [origin, `${origin}/mcp`]`` until they expire, then drop the origin. Or keep the old value with `protectedResourceHandler({ resource: origin })`.

`@clerk/mcp-tools/next` adds `withMcpAuth` and `mcpAuth`, which wrap an `mcp-handler` route handler. Import `withMcpAuth` from `@clerk/mcp-tools/next` in place of `mcp-handler`'s: it takes the handler and the options of `mcpAuthClerk` in the Express and Hono adapters, instead of a verifier function, as in `withMcpAuth(handler, { resourceUrl, clerkClient, requiredScopes, challengeScopes })`. It verifies OAuth access tokens with Clerk, including that their audience is `resourceUrl`, with the required `clerkClient` option: pass `clerkClient` from `@clerk/nextjs/server`, or a client created with both `secretKey` and `publishableKey`. It is an option rather than an import of this package, so an app without `@clerk/nextjs` still builds with `@clerk/mcp-tools/next`: webpack fails a build on any reference to a package that is not installed, even a lazy `import()`. `mcpAuth(verifyToken, options)(handler)` is the same wrapper for any authorization server. Both send the same challenges as the other adapters and set `resourceMetadataUrl` on the auth info for step-up scope challenges. When Clerk cannot verify an opaque access token at all, `withMcpAuth` throws so Next.js answers with a `500`, where `mcp-handler`'s `withMcpAuth` would answer `invalid_token`. The `@clerk/nextjs` peer dependency range now starts at 7.9.5, the first release on the `@clerk/backend` version with a reliable audience check.

**Breaking:** in `@clerk/mcp-tools/express`, `@clerk/mcp-tools/hono`, and `@clerk/mcp-tools/next`, `protectedResourceHandlerClerk` is renamed to `protectedResourceHandler` and `authServerMetadataHandlerClerk` to `authServerMetadataHandler`. Both are now factories that return the handler in every adapter, so in Express and Hono replace `app.get('/.well-known/oauth-authorization-server', authServerMetadataHandlerClerk)` with `app.get('/.well-known/oauth-authorization-server', authServerMetadataHandler())`. The old names are removed. The previous `protectedResourceHandler`, the protected resource metadata handler for an authorization server other than Clerk, is removed. For another authorization server, serve `generateProtectedResourceMetadata({ authServerUrl, resourceUrl })` from `@clerk/mcp-tools/server` in your own route, with the `resourceUrl` you pass to `mcpAuth`.

`mcpAuth` and `mcpAuthClerk` (`withMcpAuth` in Next.js) in every adapter now throw at setup unless `resourceUrl` is an `http:` or `https:` URL without credentials.

`mcpAuth` in every adapter now answers a token whose `expiresAt` has passed, or is not a finite number, with an `invalid_token` challenge, as `mcp-handler`'s `withMcpAuth` does, with an `McpTokenVerificationError` with the code `token-expired` as the failure's `cause`. Before, a `verifyToken` that returned the auth info of an expired token let the request through.

In every adapter, `protectedResourceHandler` now derives the default `resource` the same way, so that it is identical to the URL whose metadata URL the route serves, as RFC 9728 section 3.3 requires: the root route describes the bare origin, such as `https://mcp.example.com`, where the Express and Hono handlers described `https://mcp.example.com/`, and the Next.js handler keeps a trailing slash and query in the route path, as the Express and Hono handlers already did.

**Breaking:** protected resource metadata from `generateProtectedResourceMetadata`, `generateClerkProtectedResourceMetadata`, and every adapter's `protectedResourceHandler` now holds only `resource`, `authorization_servers`, and `bearer_methods_supported: ['header']`, plus any `properties`. It no longer includes `jwks_uri`, which RFC 9728 section 2 defines as the protected resource's own key set but which named the authorization server's, or `token_types_supported`, `token_introspection_endpoint`, `token_introspection_endpoint_auth_methods_supported`, `authorization_data_types_supported`, `authorization_data_locations_supported`, and `key_challenges_supported`, which are not RFC 9728 parameters and named the token endpoint as an introspection endpoint. The Clerk handlers link Clerk's documentation as `resource_documentation`, the RFC 9728 parameter, in place of `service_documentation`, which clients ignore. Pass `resource_name` in `properties` to give clients the display name RFC 9728 recommends.

**Breaking:** in `@clerk/mcp-tools/express`, `streamableHttpHandler` takes only a server factory, as in the Hono adapter. A shared server object handles only one request at a time, so passing one is now a type error and throws a `Clerk error:` when the handler is created. Replace `streamableHttpHandler(server, StreamableHTTPServerTransport)` with `streamableHttpHandler(() => createServer(), StreamableHTTPServerTransport)`, where the function returns a new `McpServer` on every call.
