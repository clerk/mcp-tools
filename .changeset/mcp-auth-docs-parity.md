'@clerk/mcp-tools': minor

**Breaking:** the exports of every entry point are renamed to follow one set of rules, taken from `@clerk/express`, `@clerk/hono`, `@clerk/nextjs`, and `@clerk/backend`. Functions are named for what they do, with no `Clerk` suffix: Clerk is the default, and another authorization server is an option on the same function. Configuration types end in `Options`. The old names are removed, with no deprecated aliases. Each adapter, `@clerk/mcp-tools/express`, `@clerk/mcp-tools/hono`, and `@clerk/mcp-tools/next`, now also exports everything `@clerk/mcp-tools/server` exports, so a server route imports from its adapter alone. Replace each old name with the new one:

`toClerkAuthInfo` behaves as `verifyClerkToken` did. It is renamed because it verifies nothing: it converts the auth object Clerk returns for a token it has already verified, from `auth({ acceptsToken: 'oauth_token' })`, into the MCP SDK's `AuthInfo`. `requireAdditionalScopes`, `isClerkAuthInfo`, and `ClerkAuthInfo` keep their names, and are now exported from every adapter as well as `@clerk/mcp-tools/server`. The client and store renames change no behavior.

These are removed with no replacement:

- In `@clerk/mcp-tools/express`, `@clerk/mcp-tools/hono`, and `@clerk/mcp-tools/next`, `protectedResourceHandler`, the protected resource metadata handler for an authorization server other than Clerk. For another authorization server, serve `generateProtectedResourceMetadata({ resourceUrl, authServerUrl })` from your own route, with the `resourceUrl` you pass to `mcpAuth`. Passing both `publishableKey` and `authServerUrl` is a type error.
- From the tools, which now come from `@clerk/mcp-tools/tools`: `SUBMIT_FEEDBACK_TOOL_NAME`, `SUBMIT_FEEDBACK_DESCRIPTION`, `submitFeedbackInputSchema`, `FEEDBACK_KINDS`, `FEEDBACK_IMPACTS`, `FeedbackToolExtra`, `CREATE_BROWSER_SESSION_TOOL_NAME`, `browserSessionInputSchema`, `browserSessionToolText`, `browserSessionErrorMessage`, and `validateBrowserSessionOptions`. The tuples `submitFeedbackTool()` and `createBrowserSessionTool()` return already carry the tool's name, description, and input schema, so register them with `server.registerTool(...submitFeedbackTool({ secretKey }))`. Everything else the two tool subpaths exported, and how the tools behave, is unchanged.
- The `main` field of `package.json`, which pointed at a directory. The package has no root entry point: import a subpath.

**Breaking:** `mcpAuth` in `@clerk/mcp-tools/express` and `@clerk/mcp-tools/hono`, and `withMcpAuth` in `@clerk/mcp-tools/next`, are each adapter's only auth entry point, and take one options type, `McpAuthOptions`, that covers both ways of verifying a token:

- Without `verifyToken`, Clerk verifies the token and checks that its audience is `resourceUrl`, which is required: `mcpAuth({ resourceUrl: 'https://mcp.example.com/mcp' })`, or `withMcpAuth(handler, { resourceUrl, clerkClient })` in Next.js.
- With `verifyToken`, your function verifies the token, `resourceUrl` is optional, and `clerkClient` is a type error: `mcpAuth({ verifyToken })`, or `withMcpAuth(handler, { verifyToken })` in Next.js. `verifyToken(token, req)` returns the MCP SDK's `AuthInfo`, or `undefined` to reject the token, with or without a promise. The token comes first and the request second in every adapter, the reverse of the `(req, bearerToken)` verifier `mcp-handler`'s `withMcpAuth` takes, so swap the parameters of a verifier you move to `withMcpAuth` from `@clerk/mcp-tools/next`: TypeScript reports the old order, and JavaScript does not.

Both take `requiredScopes` and `challengeScopes`, and Next.js also takes `onAuthFailure`. In 0.9.0, `mcpAuth` in Express and Hono took a verifier function as its first argument. Because a JavaScript caller would not see the change of meaning, `mcpAuth(verifyToken)` and `mcpAuth(verifyToken, options)` now throw a `Clerk error:` at startup that names both new call forms. `mcpAuth` passed to a route without being called, as `mcpAuthClerk` was in 0.9.0 (`app.post('/mcp', mcpAuthClerk, handler)`), throws the same kind of error on the first request instead of hanging it. `withMcpAuth` throws at startup for a missing route handler, and for a missing `resourceUrl` or `clerkClient` without `verifyToken`.

**Breaking:** in `@clerk/mcp-tools/express`, `streamableHttpHandler` takes only a server factory, as in the Hono adapter. A shared server object handles only one request at a time, so passing one is now a type error and throws a `Clerk error:` when the handler is created. Replace `streamableHttpHandler(server, StreamableHTTPServerTransport)` with `streamableHttpHandler(() => createServer(), StreamableHTTPServerTransport)`, where the function returns a new `McpServer` on every call. The Hono adapter's `streamableHttpHandler` now throws the same error for a server object when the handler is created, instead of failing on each request.

**Breaking:** `mcpAuth` in Express and Hono, without `verifyToken`, verifies OAuth access tokens with Clerk and checks that their audience is `resourceUrl`. `mcpAuthClerk` in 0.9.0 did not check the audience, so a token issued for another resource passed. Replace `app.post('/mcp', mcpAuthClerk, handler)` with `app.post('/mcp', mcpAuth({ resourceUrl: 'https://mcp.example.com/mcp' }), handler)`, using the exact URL clients use for the endpoint. The peer dependency ranges now start at `@clerk/express` 2.1.70 and `@clerk/hono` 0.1.80, because on earlier versions a JWT access token without an `aud` claim and an opaque OAuth access token both pass the audience check.

In both adapters, `mcpAuth` takes an optional `clerkClient`, created with both `secretKey` and `publishableKey`. In Express it defaults to `clerkClient` from `@clerk/express`; pass the client you gave `clerkMiddleware()` when the secret key does not come from `CLERK_SECRET_KEY`. In Hono it defaults to the client `clerkMiddleware()` sets, and without one `mcpAuth` builds its own with `createClerkClient` from `@clerk/backend`, from `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` read through Hono's `env(c)`, so `mcpAuth({ resourceUrl })` works without `clerkMiddleware()` or a client of your own, including on Cloudflare Workers, where the keys are only on `c.env`. It keeps one client for each key pair, and verifies each token once: keep `clerkMiddleware()` off the MCP route, which otherwise verifies each token a second time. Install `@clerk/backend` for this default client. The adapter loads it only when it builds the client, so a Hono app that passes `clerkClient` or `verifyToken` loads and bundles without it, and without it the default client throws `Clerk error: install @clerk/backend, or pass clerkClient to mcpAuth`, with the load error as its `cause`. Without a client and with a key missing, `mcpAuth` in Hono throws a `Clerk error:` that names the missing variable, such as `Clerk error: mcpAuth needs the CLERK_SECRET_KEY environment variable, a clerkClient option, or clerkMiddleware() to run first`, on the first request, with or without a token. In both adapters, when Clerk cannot verify an opaque access token at all, for example during an outage or with an invalid secret key, `mcpAuth` throws to the framework's error handler for a `500` instead of answering `invalid_token`, which would make clients discard a valid token and restart authorization. Clerk reports a JWKS failure on a JWT access token the same way as an invalid signature, so that case still answers `invalid_token`.

`mcpAuth` takes `resourceUrl` with `verifyToken` too, and `requiredScopes` on both paths. A token without `requiredScopes` gets a `403` with an `insufficient_scope` challenge, and `resourceUrl` sets the challenge's `resource_metadata` instead of deriving it from the request. The auth info both adapters pass on now carries `resourceMetadataUrl`, which MCP SDK 2 needs for the challenges its `scopeChallenge` tools send.

In every adapter, the `401` challenge from `mcpAuth` (`withMcpAuth` in Next.js) now lists `requiredScopes` in its `scope`, and the new `challengeScopes` option adds more, such as the scopes tools step up to, without requiring them of a token. MCP clients request those scopes when they first authorize. A request the middleware answers itself, with a `401` or `403` challenge or a `421`, records why in `res.locals.mcpAuthFailure` in Express and `c.get('mcpAuthFailure')` in Hono, and is passed to the `onAuthFailure(failure, req)` option in Next.js, whose errors and rejections are ignored so that the answer still goes out, with a `reason` of `missing_token`, `malformed_token`, `invalid_token`, `insufficient_scope`, or `misdirected_request`, for logging. `@clerk/mcp-tools/server` and every adapter export `McpTokenVerificationError`, which holds what a verifier reported for a token it did not accept. When Clerk verifies the token, its `code` is the reason Clerk gave, such as `token-verification-failed`, and its `message` is Clerk's message. It is the `cause` of an `invalid_token` failure for a token Clerk rejected, and the `cause` of the `McpAuthError` thrown when Clerk answers but cannot verify a token. A `verifyToken` can throw one to reject a token with a code of its own. It is never sent to the client.

In every adapter, `resourceUrl` can also be a list of URLs, one for each origin, for a server that answers on several hostnames. A request uses the listed URL with its origin for the challenge's `resource_metadata` and, when Clerk verifies the token, as the only audience, so a token issued for one listed URL does not pass on another. A request to any other origin gets a `421 Misdirected Request` before its token is read. `protectedResourceMetadataHandler({ resourceUrl })` applies the same rule to the metadata's `resource`, and `matchResourceUrl` applies it in a metadata route of your own.

**Breaking:** in the Express and Hono adapters, when the verifier throws anything other than an `McpTokenVerificationError`, `mcpAuth` now throws an `McpAuthError` with `reason: 'verification_failed'` and the thrown error as its `cause`, instead of the thrown error itself. `withMcpAuth` in Next.js does the same. An error handler that checks `err instanceof MyError` or reads the error's fields, including Hono's `HTTPException` handling, must read `err.cause` instead. The wrapper copies a `5xx` `status` from the thrown error, so Express's default error handler answers with it as before. Any other status is dropped and the answer is a `500`: before, a thrown error with `status: 401` reached the client as a `401` without a challenge.

`resourceUrl` can no longer have a fragment, and a query in it is now kept in the challenge's `resource_metadata`. When Clerk verifies the token, `mcpAuth` also accepts a token whose audience is the normalized form of `resourceUrl`, such as `https://mcp.example.com/` for `https://mcp.example.com`, since clients can send either, and for a root `resourceUrl` written with a trailing slash it also accepts the bare origin, which the root protected resource metadata route describes. In the Express adapter, a request without a `Host` header, or with one that does not parse, gets a `400` instead of an unhandled error or a challenge for `http://undefined`, and the request's origin comes from `req.host`, so under `trust proxy` it is read from `X-Forwarded-Host`. `@clerk/mcp-tools/server` and every adapter export the `McpResourceUrl`, `McpAuthFailure`, and `ClerkOAuthClient` types and the `McpAuthError` class, and every adapter exports its `McpAuthOptions` type.

`@clerk/backend` 3.19.0 or later is a new optional peer dependency, for the version of a client you pass as `clerkClient`: a client from an earlier version does not reliably check the audience. This package's types do not reference it, so an app that has only `@clerk/express`, `@clerk/hono`, or `@clerk/nextjs` type-checks without it. The `clerkClient` option takes the `ClerkOAuthClient` type, the part of a Clerk client that verifies tokens, and `toClerkAuthInfo` takes any object with the fields it reads from Clerk's auth object, which `MachineAuthObject<'oauth_token'>` still fits.

The `WWW-Authenticate` challenge from both adapters now quotes `resource_metadata`, which was invalid unquoted, and a rejected token now gets the challenge with `error="invalid_token"` instead of no header.

In the Express adapter, `mcpAuth` is now synchronous, so it works with or without `await`. A malformed `Authorization` header now gets a `401` challenge: before, a bare `Bearer` header returned a `500`, or hung the request with an unhandled rejection under `mcpAuthClerk`, and any other scheme was treated as a bearer token. `resource_metadata` no longer includes the request's query string.

**Breaking:** in `@clerk/mcp-tools/next`, `protectedResourceMetadataHandler`, which replaces `protectedResourceHandlerClerk`, sets `resource` from the route path and query, so `/.well-known/oauth-protected-resource/mcp` describes `<origin>/mcp` instead of the bare origin, and `/.well-known/oauth-protected-resource/mcp/` describes `<origin>/mcp/`. MCP clients send that value as the `resource` of their token request, so new tokens carry `<origin>/mcp` in their `aud` claim, and a route that checks `audience: origin` rejects them. Check the audience against the full `<origin>/mcp` URL. Tokens issued before the upgrade still carry the origin, so accept both with ``audience: [origin, `${origin}/mcp`]`` until they expire, then drop the origin. Or keep the old value with `protectedResourceMetadataHandler({ resourceUrl: origin })`.

**Breaking:** in every adapter, `protectedResourceMetadataHandler` takes an options object, `{ resourceUrl, properties }`, where `protectedResourceHandlerClerk` took the additional metadata itself. Pass the same `resourceUrl` you give `mcpAuth` or `withMcpAuth`, one URL or a list with one for each origin, and the metadata's `resource` is the URL they check for the same request: behind a proxy that terminates TLS or rewrites `Host`, the URL the route was requested at is not the public one, and clients discard metadata whose `resource` is not the URL they derived the metadata URL from (RFC 9728 section 3.3). With a list, a request to an origin none of them has gets a `421`. Without `resourceUrl`, `resource` is derived from the request as before. Move the additional metadata into `properties`: replace `protectedResourceHandlerClerk({ scopes_supported: ['email'] })` with `protectedResourceMetadataHandler({ resourceUrl: 'https://mcp.example.com/mcp', properties: { scopes_supported: ['email'] } })`. The old form is a type error and throws a `Clerk error:` when the handler is created, as does an invalid `resourceUrl`. Every adapter exports the `ProtectedResourceMetadataOptions` type.

In every adapter, `protectedResourceMetadataHandler` takes the same options as `mcpAuth` (`withMcpAuth` in Next.js), all optional, plus `properties`, so one object can be passed to both: `const options = { resourceUrl, requiredScopes: ['profile'] }`, then `mcpAuth(options)` and `protectedResourceMetadataHandler(options)`. In Next.js, export it from a module such as `lib/mcp.ts` and import it in the MCP route and the metadata route. The handler ignores `clerkClient`, `verifyToken`, and `onAuthFailure`, and checks `requiredScopes` and `challengeScopes` at startup as `mcpAuth` does. Without `scopes_supported` in `properties`, the metadata now lists `requiredScopes` then `challengeScopes`, each once, as `scopes_supported` (RFC 9728 section 2), and leaves it out when there are none, so the scopes are no longer written twice. A `scopes_supported` in `properties` is used as given, to advertise more scopes than the server asks for, but it must include every required and challenge scope: the handler throws a `Clerk error:` naming the missing ones when it is created, since a client that requests only the advertised scopes would otherwise get a `403`.

`@clerk/mcp-tools/next` adds `withMcpAuth`, which wraps an `mcp-handler` route handler. Import it from `@clerk/mcp-tools/next` in place of `mcp-handler`'s: it takes the handler and the same options as `mcpAuth` in the Express and Hono adapters, instead of a verifier function, as in `withMcpAuth(handler, { resourceUrl, clerkClient, requiredScopes, challengeScopes })`. Without `verifyToken`, it verifies OAuth access tokens with Clerk, including that their audience is `resourceUrl`, with the required `clerkClient` option: pass `clerkClient` from `@clerk/nextjs/server`, or a client created with both `secretKey` and `publishableKey`. It is an option rather than an import of this package, so an app without `@clerk/nextjs` still builds with `@clerk/mcp-tools/next`: webpack fails a build on any reference to a package that is not installed, even a lazy `import()`. `withMcpAuth(handler, { verifyToken })` uses your own verifier for any authorization server. Both send the same challenges as the other adapters and set `resourceMetadataUrl` on the auth info for step-up scope challenges. When Clerk cannot verify an opaque access token at all, `withMcpAuth` throws so Next.js answers with a `500`, where `mcp-handler`'s `withMcpAuth` would answer `invalid_token`. The `@clerk/nextjs` peer dependency range now starts at 7.9.5, the first release on the `@clerk/backend` version with a reliable audience check.

**Breaking:** in `@clerk/mcp-tools/express` and `@clerk/mcp-tools/hono`, `protectedResourceMetadataHandler` and `authorizationServerMetadataHandler` are factories that return the handler, as in Next.js, so replace `app.get('/.well-known/oauth-authorization-server', authServerMetadataHandlerClerk)` with `app.get('/.well-known/oauth-authorization-server', authorizationServerMetadataHandler())`, and `protectedResourceHandlerClerk` with `protectedResourceMetadataHandler({ resourceUrl })`. In every adapter, `authorizationServerMetadataHandler` takes no arguments, so passing it to a route without calling it, as `authServerMetadataHandlerClerk` was, throws `Clerk error: call authorizationServerMetadataHandler() and pass its result to the route` on the first request, instead of hanging the request in Express and Hono, or getting Next.js's generic error for `export const GET = authorizationServerMetadataHandler`.

`mcpAuth` and `withMcpAuth` now throw at setup unless `resourceUrl`, when given, is an `http:` or `https:` URL without credentials.

`mcpAuth` and `withMcpAuth` now answer a token whose `expiresAt` has passed, or is not a finite number, with an `invalid_token` challenge, as `mcp-handler`'s `withMcpAuth` does, with an `McpTokenVerificationError` with the code `token-expired` as the failure's `cause`. Before, a `verifyToken` that returned the auth info of an expired token let the request through.

In every adapter, `protectedResourceMetadataHandler` now derives the default `resource` the same way, so that it is identical to the URL whose metadata URL the route serves, as RFC 9728 section 3.3 requires: the root route describes the bare origin, such as `https://mcp.example.com`, where the Express and Hono handlers described `https://mcp.example.com/`, and the Next.js handler keeps a trailing slash and query in the route path, as the Express and Hono handlers already did.

**Breaking:** protected resource metadata from `generateProtectedResourceMetadata` and every adapter's `protectedResourceMetadataHandler` now holds only `resource`, `authorization_servers`, and `bearer_methods_supported: ['header']`, plus any `properties`. It no longer includes `jwks_uri`, which RFC 9728 section 2 defines as the protected resource's own key set but which named the authorization server's, or `token_types_supported`, `token_introspection_endpoint`, `token_introspection_endpoint_auth_methods_supported`, `authorization_data_types_supported`, `authorization_data_locations_supported`, and `key_challenges_supported`, which are not RFC 9728 parameters and named the token endpoint as an introspection endpoint. With `publishableKey`, the metadata links Clerk's documentation as `resource_documentation`, the RFC 9728 parameter, in place of `service_documentation`, which clients ignore. Pass `resource_name` in `properties` to give clients the display name RFC 9728 recommends.

In `package.json`, the `types` condition now comes first in every `exports` entry, so TypeScript finds the declarations under every module resolution mode, and `@clerk/mcp-tools/package.json` can be imported to read the package version.
