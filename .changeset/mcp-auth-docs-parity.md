---
'@clerk/mcp-tools': minor
---

**Breaking:** in `@clerk/mcp-tools/express` and `@clerk/mcp-tools/hono`, `mcpAuthClerk` is now a factory that takes `{ resourceUrl, requiredScopes }`. It verifies OAuth access tokens with Clerk and checks that their audience is `resourceUrl`. The old middleware did not check the audience, so a token issued for another resource passed. Replace `app.post('/mcp', mcpAuthClerk, handler)` with `app.post('/mcp', mcpAuthClerk({ resourceUrl: 'https://mcp.example.com/mcp' }), handler)`, using the exact URL clients use for the endpoint. The peer dependency ranges now start at `@clerk/express` 2.1.70 and `@clerk/hono` 0.1.80, because on earlier versions a JWT access token without an `aud` claim and an opaque OAuth access token both pass the audience check.

In both adapters, `mcpAuthClerk` takes an optional `clerkClient`, created with both `secretKey` and `publishableKey`. The Express `mcpAuthClerk` defaults to `clerkClient` from `@clerk/express`; pass the client you gave `clerkMiddleware()` when the secret key does not come from `CLERK_SECRET_KEY`. The Hono `mcpAuthClerk` defaults to the client `clerkMiddleware()` sets; pass a client to keep `clerkMiddleware()` off the MCP route, which otherwise verifies each token twice. In both adapters, when Clerk cannot verify an opaque access token at all, for example during an outage or with an invalid secret key, `mcpAuthClerk` throws to the framework's error handler for a `500` instead of answering `invalid_token`, which would make clients discard a valid token and restart authorization. Clerk reports a JWKS failure on a JWT access token the same way as an invalid signature, so that case still answers `invalid_token`.

`mcpAuth` in both adapters takes new optional `resourceUrl` and `requiredScopes` options. A token without `requiredScopes` gets a `403` with an `insufficient_scope` challenge, and `resourceUrl` sets the challenge's `resource_metadata` instead of deriving it from the request. The auth info both adapters pass on now carries `resourceMetadataUrl`, which MCP SDK 2 needs for the challenges its `scopeChallenge` tools send.

In every adapter, the `401` challenge from `mcpAuth` and `mcpAuthClerk` now lists `requiredScopes` in its `scope`, and the new `challengeScopes` option adds more, such as the scopes tools step up to, without requiring them of a token. MCP clients request those scopes when they first authorize. A request answered with a challenge records why in `res.locals.mcpAuthFailure` in Express and `c.get('mcpAuthFailure')` in Hono, with a `reason` of `missing_token`, `malformed_token`, `invalid_token`, or `insufficient_scope`, for logging.

In every adapter, `resourceUrl` for `mcpAuth` and `mcpAuthClerk` can also be a function of the request that returns the URL, for a server that answers on several hostnames. It is called for every request, and `mcpAuthClerk` uses its result for both the audience check and the challenge's `resource_metadata`.

**Breaking:** in every adapter, when the verifier throws, `mcpAuth` and `mcpAuthClerk` now throw an `McpAuthError`, exported from each adapter, with `reason: 'verification_failed'` and the thrown error as its `cause`, instead of the thrown error itself. An error handler that checks `err instanceof MyError` or reads the error's fields, including Hono's `HTTPException` handling, must read `err.cause` instead. The wrapper copies a numeric `status` from the thrown error, so Express's default error handler answers with the same status as before.

The Hono `streamableHttpHandler` now imports the MCP SDK transport when it handles a request, so an app that uses only the Hono auth middleware no longer bundles or loads the SDK's message schemas and zod.

The `WWW-Authenticate` challenge from both adapters now quotes `resource_metadata`, which was invalid unquoted, and a rejected token now gets the challenge with `error="invalid_token"` instead of no header.

In the Express adapter, `mcpAuth` is now synchronous, so it works with or without `await`. A malformed `Authorization` header now gets a `401` challenge: before, a bare `Bearer` header returned a `500`, or hung the request with an unhandled rejection under `mcpAuthClerk`, and any other scheme was treated as a bearer token. `resource_metadata` no longer includes the request's query string.

**Breaking:** in `@clerk/mcp-tools/next`, `protectedResourceHandler` and `protectedResourceHandlerClerk` now set `resource` from the route path, so `/.well-known/oauth-protected-resource/mcp` describes `<origin>/mcp` instead of the bare origin. MCP clients send that value as the `resource` of their token request, so new tokens carry `<origin>/mcp` in their `aud` claim, and a route that checks `audience: origin` rejects them. Check the audience against the full `<origin>/mcp` URL. Tokens issued before the upgrade still carry the origin, so accept both with ``audience: [origin, `${origin}/mcp`]`` until they expire, then drop the origin. Or keep the old value with `protectedResourceHandlerClerk({ resource: origin })`.

`@clerk/mcp-tools/next` adds `mcpAuthClerk` and `mcpAuth`, matching the Express and Hono adapters. Each takes the same options as its Express counterpart and returns a wrapper for an `mcp-handler` route handler, replacing `withMcpAuth`: `mcpAuthClerk({ resourceUrl, requiredScopes })(handler)`. `mcpAuthClerk` verifies OAuth access tokens with Clerk, including that their audience is `resourceUrl`, and defaults to `clerkClient()` from `@clerk/nextjs/server`; pass `clerkClient`, created with both `secretKey` and `publishableKey`, to use another client. Both send the same challenges as the other adapters and set `resourceMetadataUrl` on the auth info for step-up scope challenges. When Clerk cannot verify an opaque access token at all, `mcpAuthClerk` throws so Next.js answers with a `500`, where `withMcpAuth` would answer `invalid_token`. The `@clerk/nextjs` peer dependency range now starts at 7.9.5, the first release on the `@clerk/backend` version with a reliable audience check.

In `@clerk/mcp-tools/next`, `protectedResourceHandler` takes `properties`, as in the Express and Hono adapters, so the metadata's `resource` can match the `resourceUrl` of `mcpAuth`.

`mcpAuth` and `mcpAuthClerk` in every adapter now throw at setup unless `resourceUrl` is an `http:` or `https:` URL without credentials.
