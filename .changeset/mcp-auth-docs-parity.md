---
'@clerk/mcp-tools': minor
---

**Breaking:** in `@clerk/mcp-tools/express` and `@clerk/mcp-tools/hono`, `mcpAuthClerk` is now a factory that takes `{ resourceUrl, requiredScopes }`. It verifies OAuth access tokens with Clerk and checks that their audience is `resourceUrl`. The old middleware did not check the audience, so a token issued for another resource passed. Replace `app.post('/mcp', mcpAuthClerk, handler)` with `app.post('/mcp', mcpAuthClerk({ resourceUrl: 'https://mcp.example.com/mcp' }), handler)`, using the exact URL clients use for the endpoint. The peer dependency ranges now start at `@clerk/express` 2.1.70 and `@clerk/hono` 0.1.80, because on earlier versions a JWT access token without an `aud` claim and an opaque OAuth access token both pass the audience check.

The Express `mcpAuthClerk` takes an optional `clerkClient` and defaults to `clerkClient` from `@clerk/express`. Pass the client you gave `clerkMiddleware()` when the secret key does not come from `CLERK_SECRET_KEY`. In both adapters, when Clerk cannot verify a token at all, for example during an outage or with an invalid secret key, `mcpAuthClerk` throws to the framework's error handler for a `500` instead of answering `invalid_token`, which would make clients discard a valid token and restart authorization.

`mcpAuth` in both adapters takes new optional `resourceUrl` and `requiredScopes` options. A token without `requiredScopes` gets a `403` with an `insufficient_scope` challenge, and `resourceUrl` sets the challenge's `resource_metadata` instead of deriving it from the request.

The `WWW-Authenticate` challenge from both adapters now quotes `resource_metadata`, which was invalid unquoted, and a rejected token now gets the challenge with `error="invalid_token"` instead of no header.

In the Express adapter, `mcpAuth` is now synchronous, so it works with or without `await`. A malformed `Authorization` header now gets a `401` challenge: before, a bare `Bearer` header returned a `500`, or hung the request with an unhandled rejection under `mcpAuthClerk`, and any other scheme was treated as a bearer token. `resource_metadata` no longer includes the request's query string.

**Breaking:** in `@clerk/mcp-tools/next`, `protectedResourceHandler` and `protectedResourceHandlerClerk` now set `resource` from the route path, so `/.well-known/oauth-protected-resource/mcp` describes `<origin>/mcp` instead of the bare origin. MCP clients send that value as the `resource` of their token request, so new tokens carry `<origin>/mcp` in their `aud` claim, and a route that checks `audience: origin` rejects them. Check the audience against the full `<origin>/mcp` URL. Tokens issued before the upgrade still carry the origin, so accept both with ``audience: [origin, `${origin}/mcp`]`` until they expire, then drop the origin. Or keep the old value with `protectedResourceHandlerClerk({ resource: origin })`.

`@clerk/mcp-tools/next` adds `mcpAuthClerk` and `mcpAuth`, matching the Express and Hono adapters. Each takes the same options and returns a wrapper for an `mcp-handler` route handler, replacing `withMcpAuth`: `mcpAuthClerk({ resourceUrl, requiredScopes })(handler)`. `mcpAuthClerk` verifies OAuth access tokens with Clerk, including that their audience is `resourceUrl`, and defaults to `clerkClient()` from `@clerk/nextjs/server`; pass `clerkClient` to use another client. Both send the same challenges as the other adapters and set `resourceMetadataUrl` on the auth info for step-up scope challenges. When Clerk cannot verify a token at all, `mcpAuthClerk` throws so Next.js answers with a `500`, where `withMcpAuth` would answer `invalid_token`.
